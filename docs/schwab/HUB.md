# Field app hub (optional)

The app works with no server: phones pass work to each other by texted links. The **hub** adds one central, durable log,
a live view, remote assigning / reviewing / editing, and Google Translate for typed text. It is one Google Apps Script
web app plus one Google Sheet in the owner's Google account. With no hub configured the app behaves exactly as before.

This file is the contract between the server (`hub/Code.gs`), the client sync engine (`sync.mjs`) and the screens
(`live.mjs`). Change it first, then the code.

## Principles

1. **Offline first.** Every phone keeps working from its own localStorage. The hub only syncs those stores. No tap ever waits on the network.
2. **One writer per field.** Each field belongs to one role, and only that role's phones change it. That removes almost every merge conflict. Between phones of the same role, a push that carries its base (the part as that phone last had it from the hub) changes only the fields that phone changed, and a field both changed goes to the newest stamp; without a base the newest stamp wins the part.
3. **The hub is the durable log; phones keep a recent window** (crews 14 days, PM and superintendent 60 days). Older records are browsed from the hub on demand (`records`), not stored on the phone.
4. **The server enforces roles.** The client UI is not a security boundary.
5. **Deleting is PM-only and asks first.** Hours edits are PM-only.
6. Local-only fields (never synced): task `origin`, `gotAt`, `filedAt`, `updatedAt`, `news` (an office message or follow-up reached this crew phone: marked on the board until the sheet is opened).

## Roles and keys

A phone holds one key; `whoami` tells it the role. Keys are random, 32 characters of `[A-Za-z0-9]`, created by `setupHub()`.
The PM key is stored only as a SHA-256 hash and shown once. The crew and super keys are kept in Script Properties so the PM phone can
build invite links; the PM can `rotate` either one.

| Action | crew | super | pm |
| --- | :-: | :-: | :-: |
| whoami, translate | yes | yes | yes |
| pull tasks, config | yes (window; sent sheets only, never a draft) | yes | yes |
| pull shifts | own device only | own, plus today's on-site list | all |
| pull logs | own device only | yes | yes |
| pull reports, events | no | yes | yes |
| push crew part of a task | yes | yes | yes |
| push assign part, review, reply, create task | no | yes | yes |
| push config | no | yes | yes |
| push own shifts (worker rules) | yes | yes | yes |
| push own daily log (device rules) | yes | yes | yes |
| push shifts with PM rules (edit, add, rename, remove) | no | no | yes |
| push report super part | no | yes | yes |
| push report PM part (decision answers, pmReview) | no | no | yes |
| records (archive browse) | no | tasks, reports, logs | all |
| purge (hard delete), stats, keys, rotate, archive, selftest | no | no | yes |

Wrong keys: no detail in the error, and no lockout: the hub cannot tell callers apart, so a lockout would stop every phone, and a 32-character key cannot be guessed online. A right key is never refused `busy` because of wrong ones.

## Identity (devices, people, crews, tasks)

- **Devices are authenticated, never self-described.** Every phone has a private device secret: 32 random characters in its own localStorage key `schwab.device` (its own key, so an old tab rewriting settings cannot wipe it). The device id is the first 32 hex characters of SHA-256(secret). Every hub request carries `devSecret`; the server derives `ctx.dev` from it and ignores any `dev` the caller sends. Worker-rule shift writes get `device = ctx.dev` forced; pulls filter by the derived id. Knowing another phone's device id (it appears in texts and the Sheet) gives no access to it. A phone that has an older random device id and no secret creates a secret when it connects and re-labels its own local shifts; a shift already texted to the PM under the old id stays on the PM's copy for the PM to edit (documented tradeoff). Texted links without a hub stay unauthenticated by nature: the PM opens links from people they know.
- **People and crews have stable ids.** Settings hold `crews: [{id, name, lead, members}]` and `people: [{id, name, crewId}]`; `people` is the roster and the source of truth, and `crews[].members` is kept as a derived list for older versions. Names are matched (case, spacing and accent insensitive) only when someone picks or types a name; from then on the id is the identity. Two people may share a name: screens show the crew next to it, and adding a duplicate name asks first. Renaming a person or crew keeps the id, so assignments and hours history stay attached; screens show the current name, and old records keep the label they were made with.
- **Tasks link by uid.** Anything that points at a task stores its permanent `uid` and, for display, the short id at that time: shifts hold `tasks: [{uid, id}]`. Short ids are labels and may collide between office phones that worked offline: an office phone renumbers its own not-yet-sent sheet when a synced sheet has the same date and short id. So that it can, an office phone pushes a sheet the hub has never had, and that was never texted, only after that cycle's pull. If both were already sent, or both phones pushed in the same moment, both show "Same number as another sheet" until someone renames one.
- Tasks carry `crewId` and `memberIds` next to `crew` and `members`; shifts carry `pid` and `crewId` next to `who` and `crew`.
- **Round trip.** The templates (`SETTINGS_TPL`, `TASK_TPL`, `REPORT_TPL`, `SHIFT_TPL`) carry the supported synced fields; tests exercise sync, reload and backup/restore. Ordinary backups omit `hubKey`, retain the device secret and carry `schwab.hubSync` so the client can distinguish acknowledged work from unsynced edits. Restoring that secret preserves the original phone identity; use an invite, not another phone's backup, to enroll an additional device.

### Local restore and recovery

A restore stages an immutable generation containing the previous logical snapshot and the replacement values, including its sync baseline and `schwab.restoredAt`. It verifies that payload and publishes it with one head-pointer write last. Original physical keys are retained. Later writes to the selected generation use per-key overlays; selecting its parent retains the restored generation and overlays too. A failure before publication leaves the previous copy selected. A successful pointer write selects the complete staged copy, including after a crash; this relies on the browser's localStorage behavior and available storage.

An older tab can still write its original keys. A source change detected before publication refuses the restore; a change detected after publication pauses edits and sync with `restore_conflict`, retaining both copies for review. A different selected head makes a stale realm pause with `restore_changed`. This is preservation for reconciliation, not automatic merging of conflicting copies. Unreleased RC builds used in-place restore journals; a retained journal now causes a recovery hold and is exported verbatim, never automatically replayed over current data.

A device-changing restore refuses this phone's own shifts unless each is closed and its current canonical fingerprint matches the acknowledged fingerprint. This includes shifts present in an older backup and clock-outs saved before a sync scan. Missing acknowledgments are uncertain, including lost replies; they are not permission to relabel a shift. Notes and their per-note facts are retained, and sent/acknowledged provenance is not reset by an older backup. An attempted note without a receipt blocks a destructive identity change. A saved v2 push must be resolved on its original connection before restore.

Jobs keeps navigation and clock-out links accessible. Exporting recovery copies or selecting the original requires office authorization, checked again after the selection confirmation. Healthy office sessions may use these controls; a paused or damaged selected copy can verify an existing scoped office PIN for recovery only, with an original physical PIN/settings fallback when necessary. Recovery never creates a replacement PIN or resumes edits/sync. Its grant is limited to that realm and expires; reload requires verification again. Retry limits and revocation state are separate from the retained data. If no valid existing PIN can be verified, the copies remain for owner recovery rather than offering an unlock bypass.

Recovery downloads contain raw retained bytes, including credentials that ordinary backups omit. Keep them private and scope them to owner review. Retained generations consume browser storage and are not automatically deleted. Clearing browser/site data or losing the device can still lose local copies; keep independent backups.

Compatibility tests include an unmodified v18 client replaying a saved note request without changing its wire body or operation id. Such a client still reads original physical keys, not the newer selected generation; an older client writing there requires reconciliation before the new copy resumes. These checks do not establish arbitrary PM Worker, Hub or database rollback safety. Preserve their schema and receipt contracts and validate server rollback separately. Historical rows without reliable clock-out provenance can require owner review; a client update cannot reconstruct missing history.

## Entities

### Task (key `uid`)
- **Office part** (super, pm): `ASSIGN` fields (`id date by floor area crew members size scope refs allot allotNote est estNote pStart pStop checkIn`), the structure of `items` and `checks` (their `id` and `text`), `review reviewer followUp`, the new `reply replyAt replyBy`, `aLang` (the language the office part was first typed in), `aLangs` (the language of each office text by its field or step id, `{scope:'es', reply:'en', <step id>:'es'}`), `sentAt`, stamp `assignAt`.
- **Crew part** (any role): `CREW` fields (`lead aStart aStop delay status doneText remain comments cLang cLangs resultAt`), `done` and `at` of every item and check, stamp `crewAt`. `cLangs` is `aLangs` for the crew's texts (`doneText remain comments`).
- `aLangs` and `cLangs` hold only `'en'` or `'es'` under a field name or a step id (at most 300). With a base they merge key by key like the fields, so a push that did not touch a text never relabels it.
- A push replaces a part only if the incoming stamp is >= the stored stamp (ties: incoming wins). The server clamps a stamp more than 5 minutes ahead of server time to server time.
- A crew key sending office fields has them ignored (`forbidden` is reported for the entity only if nothing else applied).
- Checklist merge: office structure wins for which items exist; done and at come from the stored crew part by item `id`. A new item starts not done.
- Two phones on one crew: a crew part push may carry `crewBase`, the crew part (crew fields, `items` and `checks` as `{id, done, at}`, ticked ones only) as that phone last had it from the hub. With it, only the fields and steps the phone changed since then are applied, each where the stored value is still the base's or the push's stamp passes the rule above; so a phone that has not pulled yet never wipes another phone's taps, and a value both changed goes to the newer stamp. Without it the whole part follows the stamp rule.
- Two office phones: an office part push may carry `assignBase` the same way (the office fields, `items` and `checks` as `{id, text}`). With it, only the fields the phone changed since are applied as above, and the steps merge by id: steps it added or reworded go in, steps it took out leave unless the other phone reworded them since the base (then they stay, reworded, as a report entry does), and another phone's added, reworded or removed steps stay so. The roster, floors and checks in the settings merge the same way (a crew's `members` text is rewritten from the roster by every phone, so it never counts as a change that keeps a crew another phone took out). So the superintendent fixing a floor never wipes the PM's message, and an offline edit comes back without undoing the newer one. Without it the whole part follows the stamp rule. A push too big with its bases goes without them.
- Delete: PM `purge` (also reachable as `deleted` in a push by pm). The server keeps a tombstone 90 days so phones remove it on their next pull.
- Crew phones show the task as `origin: 'link'`; office phones as `origin: 'mine'`. A crew copy on a phone that now holds an office key (it opened the text, or joined by a crew invite, before it connected as an office phone) becomes `'mine'` when the hub copy arrives.

### Shift (key `id`; fields as `SHIFT_TPL` in shared.mjs: `id device who date in out crew tasks edited{who,in,out} gone at`)
- `crew` (the crew the person is on, from the roster) and `tasks` (task IDs they were assigned that day, e.g. `["T1019-02"]`) are set by the worker's phone at clock-in and clock-out and follow the same worker rules as `in`; the PM can change them. Names are matched to the roster (Settings crew members) case- and accent-insensitively.
- **Worker rules** (any key, shifts made by the device authenticated by `devSecret`; see Identity): new id is always added, even when the PM has already entered that person's day by hand: those are the real punches, so both shifts show on the PM's timesheet (and in Activity) for the PM to see and settle, and the worker's clock keeps its own. An hours text opened on a hub PM phone adds them the same way (it never files them removed), and Crew hours and Send to accountant flag such a day, so it is not counted twice unseen. Existing id: only if the stored `device` matches; updates `who` only if `at` is newer and `edited.who` is false; `in` and `out` follow the phone unless `edited.in` / `edited.out`; an older text never undoes a clock-out; `gone` shifts are never revived. The client never sets `edited` or `gone` for itself: the server sets `edited` flags false for worker pushes. **Clock-out provenance:** a worker push's `out` is only that phone's own Clock out tap, marked `tapped: true`; a PM time the phone pulled (`edited.out`) is never sent as its own (a tap not on the hub yet stays shown on the phone, unflagged, until its push is acknowledged; then the PM time shows). The Clock out button closes only the latest shift: one a clear reopened under a later shift stays a missed clock-out, and Crew hours refuses that clear. The hub keeps the worker's last own clock-out in `punch` even under a PM time, and the clock-outs a PM typed in `pmOuts` (both the hub's own; a phone's copy is never read). An `out` without `tapped` that is one of `pmOuts` is an older phone repeating the PM time, never a punch. A clock-out on a shift a PM clear reopened is refused (`later_shift`) when the same phone has a later shift that began before that clock-out: an older phone offers to close its latest open shift, and the clear may have come while the later shift was still offline, out of reach of the clear's own guard; the shift stays a missed clock-out for the PM to type (the older phone's own copy keeps the refused time, reported once). On a row from before these fields an unflagged `out` is the worker's punch.
- **PM rules** (pm key): the shift is stored as sent (fields validated), including `edited`, `gone`, and PM-added shifts (empty `device`). A PM push carries `pmAt`, the PM phone's edit stamp (the hub keeps the newest; phones do not store it), and `base`, the shift as that PM phone last had it from the hub. With a base, only what that phone changed since is applied, field by field (`who`, `in`, `out` each with its `edited` flag; `pid crew crewId tasks date gone`), and a value both changed goes to the newer `pmAt`: a fix on a PM laptop and one on the PM phone both stand, and a PM phone that has not pulled a clock-out or a newer name yet changes neither; a blank `out` with `edited.out` false is never a change to a worker's punch (a shift with a `device`), so an Out box cleared on Crew hours cannot erase a clock-out, except that clearing a clock-out the PM typed (the base has `edited.out`) takes the PM time back by the same newer-`pmAt` rule: `out` becomes `punch` (blank: the shift is open again and the worker's next tap counts) with `edited.out` false; a shift the PM added is the PM's to clear. An unflagged `out` from a PM push is the worker's (a relayed hours text) and becomes `punch`, unless it is one of `pmOuts`; a push without a base never takes back a PM time. A clear that would reopen a shift whose phone has clocked in again after it (a later shift of that device within the next day) is refused (`later_shift`) and the PM time stays: a phone still on a version before clock-out provenance clocks out its latest open shift and would close the reopened one, counting those hours twice; the PM types the time they left instead. Rolling the hub back to a version before provenance drops `punch` and `pmOuts` and this guard. Without one, an older `pmAt` changes nothing, and a newer one is stored as sent, except that it never erases a clock-out the phone has not pulled yet nor undoes a newer name from the worker's phone.
- **Which rules**: a push carrying `pmAt` (the PM's timesheet) goes by PM rules, also for a shift of the PM phone's own clock, an Undo with every flag clear included; the PM phone's own clock taps carry no `pmAt` and go by worker rules. The PM phone sends a shift of its own clock from the timesheet only when it was corrected or removed there: an `edited` flag, `gone`, or its `who`, `date`, `in`, `out`, flags or `gone` differ from its hub base. A `pid`, crew or task link filled in on the phone (attachPeople, when the roster knows the name) goes up from its own clock, never as a PM edit, so Activity never says "PM edited" for it.
- Hours math is identical on client and server: clock-in to clock-out in real minutes (DST-correct, overnight = next morning), payroll hundredths `round(minutes * 5 / 3)` per shift, summed (`cents` in report.mjs). The server's timezone is America/New_York (the job's).

### Log (key `uid`; fields `uid date device pid who crewId crew body hours at`)
- A worker's daily entry: one per phone per day. The key is the phone and the day: `uid = 'wl-' + <first 12 characters of the device id> + '-' + date` (26 characters), so a phone can only ever write its own days, and writing the same day twice is one record (creation is idempotent). `who`, `crew` are the labels at the time (trimmed to 60), `pid`, `crewId` the roster ids; `body` is long text; `hours` is a number, clamped to 0 to 24 in hundredths; `at` is the phone's stamp (clamped like every stamp).
- **Device rules** (any key, the phone authenticated by `devSecret`; see Identity): no secret is `device`; a uid that is not `logUid_(this device, its date)` is `forbidden`; the stored `device` is forced to the proven one. A push whose `at` is older than the stored entry changes nothing, and the reply carries the stored (newer) copy. There is no office part: the PM reads logs, never edits them (delete is `purge`, as for everything).
- One event, `log.created`, when the day's entry first lands ("Dana R started a daily log for 2026-10-19", ref the uid, the Activity tab's Ref cell shows the name). Later edits (autosave) write no event.
- Pull: a crew key gets its own device's logs in the window; super and pm (so the bridge too) get every log. `records {kind: 'logs', who: <device id>}` lists one phone's entries (`who` also matches the name and the person id).

### Note (key `uid`; fields `uid date device pid who crewId crew task tid body lang at texted`) — a permanent message to the office
- A message a phone sends to the office about a sheet (`task` = the sheet's `uid`, `tid` = its short id as a label) or about the day (`task` and `tid` empty). It is the crew's answer to an update that reached them by itself: no text, no link. **Notes are permanent**: once the hub stores one, nothing a phone sends changes it; only the PM's `purge` removes it (as for every record).
- The key is the phone plus a random part: `uid = 'wn-' + <first 12 characters of the device id> + '-' + <10 random [a-z0-9]>` (26 characters), so a phone can only ever write its own notes.
- **Device rules** (any key, the phone authenticated by `devSecret`; see Identity): no secret is `device`; a uid that does not start with `'wn-' + <this device's 12 characters> + '-'` is `forbidden`; the stored `device` is forced to the proven one. A uid the hub already has changes nothing and the reply carries the stored copy (status `ok`): a resend after a lost reply is harmless. The bridge (v2 server principal) may not write notes (`forbidden`).
- Fields: `body` is trimmed text of 1 to 1,000 characters (as the office's Message, `MSG_MAX`; empty is `invalid`, longer is clipped); `who`, `crew` trimmed to 60; `pid`, `crewId`, `task` are ids (else ''); `tid` at most 20 characters; `lang` `'en'`, `'es'` or ''; `at` the phone's stamp (clamped like every stamp); `date` the day it was written, which follows `at`: a date more than a day away from the day of the clamped `at` (script time zone) is replaced by that day, so a wrong phone clock cannot hide a note from every window or keep it from ever being archived; `texted` true when the note already reached the office by text (it was written with no hub; office phones store it as seen).
- One event per note, `note.created`: "<who> to the office on <tid>: <first 120 characters>" (ref the task uid, Ref cell the tid; a day note says "about <date>"). The PM Live feed and the Activity tab show it.
- Pull: a crew key gets its own device's notes in the window; super and pm (so the bridge too) get every note. A full pull (`since` 0) takes the window; a pull after `since` takes every note with a newer revision, whatever its date, so a note that arrives late (written offline before the window) still reaches the office. An office phone keeps such a note until it has shown it. `records {kind: 'notes'}` lists them (super and pm; `who` matches the name, person id or device id).
- Sheet tab **Messages**: When, Date, Name, Crew, Task, Message, then `key rev data`. On a Sheet made before this tab existed it is added by the first note push (Script Property `NOTES_TAB`, as `LOGS_TAB`); new jobs get it at setup.
- Archive moves notes with the same date cut as logs; `stats` counts them (`rows.notes` once the tab exists); `purge {kind:'notes'}` is the PM's. A push of a note is never refused for the archive cut (`ARCHIVED_BEFORE`): a note never changes, so a resend cannot bring back an older copy, and one written offline before the cut still reaches the office. A resend of a note already archived (its reply was lost) is stored again as a live row; nothing is lost.
- `configureFieldHubJob` adds any missing tab before it formats a job's Sheet (a creation begun by an older version has no Messages tab).
- An older hub that does not know notes answers a push without a `notes` list: the phone keeps the note as not sent and says the hub needs its update, never that the office has it.

### Report (key `date`)
- **Super part**: everything except the PM part; stamp `updatedAt`.
- **PM part**: `decisions[].pm` and `pmNote` (matched by `q`), `pmReview`, `pmLang`; stamp new `pmAt`. A PM part push carries `pmBase`, the PM part (`pmReview`, `pmLang`, `decisions` as `{q, pm, pmNote}`) as that PM device last had it from the hub, or `null` (a blank base). With it, only the answers (each `[pm, pmNote]` by `q`), `pmReview` and `pmLang` it changed since are applied, as with `supBase`: a PM phone and a PM laptop answering different decisions both stand, and one both changed goes to the newer `pmAt`. Without it the newer `pmAt` takes the whole part. The stored `pmAt` is the PM part's version: a push that changes it moves it past the stored one even when its own stamp is older (the larger of stored + 1 and the push's), so a phone that has not pulled that answer never holds it as seen.
- Same replace-if-newer rule per part. `lang` records the language the superintendent's part was written in, `pmLang` the PM's.
- A super part push carries `supBase`, the super part (`decisions` as `{q, rec, by}`) as that phone last had it from the hub, or `null` when it never had one (a blank base: everything it has, it added). With it, only what the phone changed since is applied, as with a sheet's `assignBase`: each field, and in `needs`, `decisions`, `floors` (and each floor's `crews`), `next` and `risks` each entry, matched by its first field (`item`, `q`, `floor`, `name`, `step`, `risk`; the nth of a repeated one to the nth). Another phone's added entries stay, and an entry one phone took out and the other changed stays. So the PM typing one line never wipes the superintendent's report, offline or not. Without `supBase` (a push too big with it) the whole part follows the stamp rule.
- A decision is matched by its super fields only (`q rec by`); its PM answer is not part of the super part. `supBase.pmAt` is the PM part stamp that phone last had: when it is the stored `pmAt` or newer, a decision the phone took out or reworded goes, answer and all, so the superintendent can remove or reword a question the PM answered. Otherwise (the PM answered since, or no `supBase`) an answered decision the push left out is kept as its own entry: an answer is never dropped unseen.
- A cleared report (purge) leaves its day open: a push with `supBase: null` and a super part stamp is that day's new report, so it is stored and the day's tombstone is removed (a phone that missed the clear then gets the new report, not a delete). A push from a phone holding the cleared copy is still refused `deleted`; the phone drops that record at once, as the tombstone would.

### Config (single document)
Synced by super or pm: `project site super pm floors crews people checks pin` (`pin` is the office passcode hash, so a new crew phone can show a lock). Never `folderUrl`, `siteCode`, `hubKey`. Crew phones read it for the crew list and floors.
A push may carry `base`, the settings as that phone last had them from the hub. With it, only what the phone changed since is applied, as with a sheet's `assignBase`: each field it changed, and in `people`, `crews` (by id), `floors` and `checks` (by text) the entries it added, changed or removed; another office phone's changes stay. Without it the newer `at` takes the whole document.

### Event (server-written, append only)
`rev, ts, who, role, kind, text, ref`. Written by the server from what changed: task created, started (`aStart` first set), status set (Complete, Partial, Blocked), reviewed, replied; clock in, clock out, PM edit; report sent. `text` is a short English line. The PM Live feed shows them newest first.

## Transport and API

`POST` to the web app URL, body = JSON as `text/plain` (a "simple" request, no CORS preflight). Reply is JSON: `{ok:true, ...}` or `{ok:false, error, message}`, `error` one of `bad_request unauthorized forbidden busy too_large quota not_ready server`. Request: `{v:1, key, action, dev, ...}`. Size caps: body 1,000,000 characters, 200 entities per push, one entity's JSON 45,000 characters (a sheet cell holds 50,000), lists 500 as everywhere else. All times `Date.now()` ms; dates `YYYY-MM-DD`; times `HH:MM`.

| action | request extras | reply extras |
| --- | --- | --- |
| `whoami` | | `role, name?, rev, now, tz, version, sheetUrl?` (pm) |
| `pull` | `since` (rev, 0 = full), `days` (default 14, max 90), `crews?`, `pid?` | `rev, now, same?:true` when nothing changed; else `tasks[], shifts[], reports[], logs[], config?, events[], deleted[{kind,key,rev}], onsite?[{who,in,date}]` (super). Every entity carries its `rev`. A crew phone sends its person's crew on the roster (else the crew it joined) as `crews`, and their roster id as `pid`: a sheet whose `memberIds` lists that person comes too, whatever its crew. With `crews`, a sent sheet that changed and is now another roster crew's (and does not list `pid`) is listed in `deleted` with `moved: true`, so it leaves the old crew's phones; a phone keeps one it got only by text, or one with work it has not pushed yet (that work goes up first, and the sheet leaves on a later pull). |
| `push` | `tasks[], shifts[], reports[], logs[], config?, deleted[{kind,key}]` (pm) | `rev, tasks[{key,status:'ok'\|'rejected',reason?,task?}], shifts[...], reports[...], logs[{key,status,reason?,log?}], config?` with each entity's canonical merged copy |
| `translate` | `items[]` (max 25, each text <= 2000 chars), `from`, `to` ('en'\|'es') | `items[]` same order, `cached?:n`. Error `quota` when Google's daily limit is hit. |
| `records` | `kind, from, to, who?, q?, cursor?` | `items[]` (<= 200), `cursor?` |
| `purge` (pm) | `kind, key` | `rev` |
| `stats` (pm) | | `rows{tasks,shifts,reports,events,logs?}, cells, cellLimit, sheetUrl` (`logs` once the Daily log tab exists) |
| `keys` (pm) | | `crew, super` |
| `rotate` (pm) | `role:'crew'\|'super'` | `key` |
| `archive` (pm) | `before:'YYYY-MM-DD'` | `sheetUrl, moved{...}` (creates an archive Sheet and moves older rows into it) |
| `selftest` (pm) | | `checks[{name,ok,detail}]`: write, read, merge rules, translate a sentence containing a drawing number, delete |

`rev` is one global counter in Script Properties, bumped by every write; a no-change `pull` costs one property read.

## Protocol details, as built (wave 1)

- `purge` names the record as `target` (the request's `key` is always the credential). Kinds are plural on output (`tasks shifts reports logs`, `events` in records), singular accepted on input.
- Push results carry `i` (index in the request list); `key` is '' when the sent key had an unsafe shape. Refusal reasons are a fixed list: `forbidden invalid too_large device deleted archived`. Caps apply per kind (200 each) plus the 1,000,000 character body cap.
- A part stamp of 0 means "not sent" and never replaces a stored part. A key writing the other role's part (an office key editing the crew part, the PM editing the super part of a report) needs a strictly newer stamp; ties go to the incoming copy only for the part's own role.
- Every task push carries `uid` and `date`. A crew phone's push carries only those plus crew fields and ticks.
- Shift `crew`, `tasks` (and `pid`, `crewId`) follow the phone only until the PM has touched the shift (any `edited` flag).
- Config carries an `at` stamp; first contact adopts the hub's config instead of pushing a phone's defaults.
- Pulls cap lists at 500 and then return `more: true` with the `rev` actually covered. First cycle after connect (or a role, crew or window change) is pull, push, pull. On an office phone, a new unsent sheet the hub has never had goes up after the cycle's pull (push, pull, push, pull), so a synced sheet with its day and number renumbers it first (Identity).
- Deletion is only ever an explicit `purge` (never inferred from a missing local copy); a tombstone reaches other phones on their next pull. A sheet moved to another crew reaches the old crew's phones the same way (see `pull`).
- Archive moves hours in whole Monday to Sunday weeks; a later push of an archived record is refused with `archived`. It copies every row into the archive Sheet first, then keeps a receipt in the Script Property `ARCHIVE_PENDING` until the rows are deleted here and the archive horizons are saved. If that part fails, the next write of any kind finishes it first, under the lock, so an old record is never revived meanwhile; an archive retried for the same date answers from the receipt instead of copying again (its "Archived N rows" Activity line can then show twice). A write that touches hours sets `WEEKLY_DIRTY` until Weekly totals are rebuilt, and the next write rebuilds them first.
- **Recovery** when every write keeps failing (`server`) because one of those repairs keeps failing: in the script editor, Project Settings > Script Properties, delete `WEEKLY_DIRTY` (Weekly totals wait for the next hours write to be rebuilt), or copy the value of `ARCHIVE_PENDING` (it names the archive Sheet and the date) and delete it (rows it had not deleted yet stay in the live Sheet as well as in that archive copy; once writes work, Archive for that date again, which moves them into a new archive Sheet).
- Rate caps: 40 pushes a minute per phone, 300 per key (`busy`). A wrong key is retried every 10 minutes, not on the short backoff. A join link must carry the role `whoami` reports; PM links are refused (the PM key never travels).

## Client identity API (shared.mjs) used by sync.mjs, live.mjs and report.mjs

- Device: `ensureDevice()` (async; creates `schwab.device` = `{secret, id}` once: secret 32 characters `[A-Za-z0-9]` from `crypto.getRandomValues`, id = first 32 hex characters of SHA-256(secret)); `deviceId()` and `deviceSecret()` read it synchronously ('' until ensured). A phone with an older random `settings.device` keeps working without a hub (texted links); when it first connects, its own local shifts are relabeled from the old id to the new one.
- Requests to the hub carry `devSecret`; the hub derives the device. Shifts store the derived id in `device`.
- People and crews: `SETTINGS_TPL.crews = [{id, name, lead, members}]`, `SETTINGS_TPL.people = [{id, name, crewId}]`. On load, settings without `people` take them from this phone's `schwab.roster` (a copy written with every settings save, so a tab still on an older version cannot re-key or shorten the roster; crews match by name), else they are migrated from the crews' `members` strings, and every crew gets an id; `members` stays derived (comma list of that crew's people) for older versions. Helpers: `people(S)` -> `[{id, name, crewId, crew}]`, `personById(S, id)`, `crewById(S, id)`, `findPerson(S, name)` (nameKey match; among duplicates it prefers the given crewId), `addPerson(S, name, crewId)`, and renames that keep ids.
- Tasks: `crewId`, `memberIds` next to `crew`, `members`. Shifts: `pid`, `crewId`, `tasks: [{uid, id}]` (a legacy string id becomes `{uid: '', id}`).
- `byPerson(shifts, l, S)` groups by `pid` when present, else by nameKey of `who`; the label is the roster's current name for that pid, else the first spelling seen.
- Hub config carries `people` and `crews` with their ids.

Readable tabs, each with a bold frozen header; the machine copy is the last column `data` (JSON), before it `key` and `rev`:

## Client contract (`sync.mjs`)

Settings gain `hubUrl`, `hubKey`, `hubRole` (set after `whoami`), `hubCrew` (crew phones: the crew they joined), `device` (exists). Stores gain nothing new except the fields named above.
- **Detection by diff, not by hooks.** The engine reads the local stores straight from localStorage (`KEYS.tasks`, `KEYS.hours`, `KEYS.crewHours`, `KEYS.reports`, `KEYS.settings`), hashes each entity, and pushes the ones whose hash differs from `schwab.hubSync.hashes[key]`. `poke()` (debounced 1.5 s) is called after the app saves, but correctness never depends on it: a 20 s timer and visibility, online and focus events also run a cycle.
- **Cycle** = push dirty entities, then `pull`. Pulled entities are merged into the local stores by the ownership rules above and saved; then `onChange(kinds)` is called synchronously so the app reloads its in-memory copies (`T`, `R`, `MY`, `CREW`) before any further tap. The app must not re-render under a focused text field: if one is focused it waits for blur.
- **Merging** (per part of a sheet, report or the settings): a version this phone already holds is skipped, and a part with no unsynced edit here takes the hub's. An unsynced edit stays over another hub copy when its stamp is newer, or when it changed since its base (`assignBase`, `crewBase`, `supBase`, `pmBase`, the settings' `base`): its push then sends only what changed, and the hub merges that field by field. A part kept this way is not recorded as seen, so its next push still names the PM part this phone last merged (`supBase.pmAt`): an answer from another PM device is never taken as seen. A part still as its base (a texted copy, below) has nothing to merge, so a newer hub copy replaces it. The push reply's canonical copy of each entity is merged the same way when it differs from what went up (another phone's fields, or a field both changed that went to the newer stamp), so the phone never shows its own value as synced while the hub kept another: the pull may already be past that revision (a pull-first round), or the hub changed nothing and has no new revision to send.
- Offline or error: nothing is lost (dirty set persists); status goes to `offline`; retries back off 5, 10, 20, 40, 60 s. A rejected entity is reported once and then left alone until it changes; one refused `deleted` leaves the phone quietly, as its tombstone would, since a phone already past that tombstone would never get it again. No phone pushes a sheet the hub never had without its office part (a crew phone: one texted by an office phone that is not on the hub), so a crew part alone never makes a blank sheet there; it counts as not sent. Connect, invite and the PM's one-off actions (purge, rotate, records, stats, archive, selftest) are not retried, so their failure reads "That did not work. Try again." (Settings > Hub's Connect adds that a hub it cannot reach may still be set to Who has access: Only myself); "Check the hub link" is said only when connecting, or for a page not found.
- **Another hub, or none**: disconnecting keeps everything the phone knew of that hub, and joining the same hub again picks up where it left off, so work not sent yet goes up first and merges with its bases (a crew tick never loses to another phone's tick on another step). Connecting to a different hub address keeps what the old hub had of each record (hashes, stamps and bases, not the refusals, the sync position or the settings), so what this phone already synced (another job's sheets and reports) is not uploaded to the new hub; the first round there is pull-first. Either way, edits made while disconnected go up ranked by when they were made (not by when the phone came back). A sheet saved by a tab of a version before the hub (no `assignAt`) never has its office part pushed: the next pull is a full one and brings the hub's copy back.
- **Roles on a phone**: `crew` role phones write only the crew part of tasks and their own shifts; the engine does not even attempt office fields. `super` and `pm` phones write what their role allows. A part the phone's role does not write is left as the hub last had it, never counted as sent, so a phone that joins the same hub again in another role (the superintendent who opened a crew invite, then his own) sends every part the new role writes that the hub does not have. Settings > Hub's Connect refuses the crew key (crew phones join by invite), a phone set to Project manager connects with the PM key only (Connect or an invite: its review and timesheet would never go up, and the first pull would blank them), refused before anything on the phone changes, and a signed-in phone the hub knows as a crew phone says so on Live and Tasks. The PM phone is the only one whose local `crewHours` store (the timesheet) is pushed with PM rules.
- **Window**: after a pull, local entities older than the window and not dirty are dropped from the phone (they remain in the hub).
- **Texts on a hub phone**: Send to crew, Send results, the day plan and the daily report still open a text. A text is a copy of what the hub delivers, so where it would change a sheet or report this phone has, `fromText(kind, key, part, at, skew)` decides: a part this phone already holds from the hub (or has an unsynced edit of) as new as the text's own time (`sentAt`, `resultAt`, the sheet's or report's `updatedAt`) is kept and the person is told so (a day plan judges each sheet by its office part's own stamp, which the sending phone puts in `assignAt`: `officeAt(t)`, never a pulled crew tick); otherwise the text is merged, and its change goes up stamped with the text's time, never the time it was opened, so newer work on the hub wins over it. A text made on a hub phone carries `skew` (that phone's hub time minus its clock, `hubStatus().skew`), so its time is read in hub time; a report text from a phone with no hub carries none. A results text for a sheet this phone does not hold yet sends its office part stamped as old as the copy it carries (its `assignAt`, else `sentAt`). A report text from a hub phone opened on a phone with no copy of that day is that phone's copy of the hub's report (its sender sends its own work up), so it is both parts' base (`supBase`, `pmBase`): an old text brings back nothing the hub took out since, nor a report the PM cleared. One from a phone with no hub has no base: everything in it is new to the hub. A sheet new to this phone from a hub phone's day plan text is the same: the text is both parts' base, so only what is changed here after goes up, never the whole office part stamped as the edit here; a results text's is its office part's base, and its crew part (the crew's own results) goes up from here by its stamp. A task text (Send to crew) opened on an office phone (pm or super key) that does not hold the sheet makes the office's sheet (`origin: 'mine'`), never a crew copy; from a hub phone it is a copy of the hub's, so it is both parts' base, as a day plan's. Such a copy, until it is changed here, never keeps its part over a newer hub copy, even when the text is opened in the middle of a round (Merging). A sheet or day plan text from a phone with no hub carries no `skew` either.
- **Notes** (a key per note, `schwab.note/<uid>`, and a key per fact about it, `schwab.noteFact/<uid>/<fact>`): the phone's own notes, and on an office phone every note pulled. `addNote({task, tid, body})` saves a note on the phone at once (stamped, its uid made from this device) and pokes a round; a note is pushed until the hub's reply carries it with status `ok` (then it is never pushed again; it cannot change) and is reported once if refused. Pulled notes merge by uid (a stored copy never changes). **A note the hub has not acknowledged is never dropped**: not by the date window, a restart, a disconnect, a backup (backups carry every note and fact key) or a restore). A restore writes the backup's note and fact keys and takes none away: every note on this phone stays, with every fact known of it (an older backup never makes a note sent since look unsent). A backup from another phone replaces this phone's device id, and the hub takes a note only from the phone its uid names: one of this phone's own the hub kept stays as kept; one never sent goes on as the restored phone's (uid and device follow the device id, its facts move with it, nothing else changes); while one was sent but not confirmed (it may be on the hub after a lost reply) the restore is refused and says to connect first. Only acknowledged notes older than the window that this phone has shown leave the phone. **No key is read, changed and written back**: each tab reads its own copy of localStorage and other tabs' writes reach it later, so a shared list could lose a tab's write, under Web Locks too (real Chrome lost 5 of 600 locked counter updates in two tabs). A note's key is written once (by the phone that wrote it, or by a pull, with the same words); a fact (`s` kept by the hub, `x` refused, `old` an older hub answered, `a` sent at least once, `t` went by text, `seen`) is a key that one value fills, and `s` outranks `x` and `old`; a state saved by a round writes only the facts it added. A note leaves with all its keys. So two open tabs never undo each other's notes, with Web Locks or without (iOS before 15.4); Web Locks, where there are some, still order a restore and the writes around one note. A merge that will not save puts its other stores back and takes no note away. A tab still on a version before notes never touches these keys. A note that went by text with no hub is marked, and goes up `texted` when the phone joins a hub. If the phone cannot store a note, the typed text stays in the box and nothing says sent. A lost reply is retried with the same uid; the hub answers with the stored copy, and the phone shows "Kept on the hub" only when that reply carries this uid with status `ok`. Delivery is by the app's own rounds while it is open (and on return to the foreground); nothing is pushed to a phone that is asleep or closed. `noteState(uid)`: `'hub'` (the hub has it), `'waiting'` (saved here, not sent yet), `'old-hub'` (the hub answered without notes: it needs its update), `'refused'`. An office phone keeps a local-only `seen` mark per note (never synced) so the board and Live can say a message is new; a note this phone wrote, or one marked `texted`, is seen from the start. A note the hub refuses as `deleted` (purged after a lost reply) is not announced; one it could not read (no key in the reply) is matched by its place in the request and refused once. A body of only spaces or control characters is empty on the phone too.
- **Updates reach crew phones by themselves.** A sent sheet's office part that changes after the crew phone already had it (scope, steps, times, crew, floor, area, members, checks; not the office's review) marks the sheet on the crew phone as updated (`news: 'update'`; an office message or follow-up stays `news: true`) and says "The office updated sheet {id}" once per round. Nothing has to be sent again.
- **Status** for the header dot: `off` (no hub), `live` (last cycle ok, < 60 s ago), `syncing`, `offline`, `error` (bad key or server problem; message).
- Exports: `initHub({ S, onChange, toast })`, `hubStatus()`, `poke()`, `cycle()`, `joinFrom(data)`, `connect(url, key)` (runs `whoami`, saves role), `disconnect()`, `invite(role, crew?, crews?, people?)` (returns an app link `#p=` of kind `join`), `translate(items, from, to)`, `records(query)`, `stats()`, `purge(kind, key)`, `purgeLater(kind, key, due)` (a PM delete waiting out its Undo, stored so it is sent once due even after the app was closed; due 0 takes it back), `onHub(key, kind?)` (the hub has this sheet, or with `'report'` this report), `replyOnHub(t)` (the hub took this sheet's message as it is here: Live says sent only then), `rotate(role)`, `archive(before)`, `selftest()`, `fromText(kind, key, part, at, skew?, copy?, parts?)`, `officeAt(t)`.
- **Join link** (kind `join`): `{v:1, kind:'join', hub:{url, key}, role, crew?, crews?, people?}` (`crews`: the job's crew names, for an invite where the person picks; a new phone knows only its defaults. `people`: `[{name, crew}]`, the crew's people from the PM's roster, or everyone's for a "they pick" invite, so the person taps their name as the roster spells it; a typed name is matched to it, and one the roster does not have is questioned once). Opening it on a phone saves the hub settings, runs `whoami`, and asks (once) for the person's name: on a crew phone also the crew; on the superintendent's it is the name on the sheets they assign and their own time clock. The PM phone never trades its key for an invite to its own hub (its key was shown only once). The invite is deliberate and PM-initiated; the crew key can only do crew-level things, and `rotate` kills a lost phone's access.

## Translation

- Typed text keeps the language it was written in (a sheet's `aLangs`/`cLangs` per text, else its part's `aLang`/`cLang`; a report's `lang` and `pmLang`; missing means `'en'`). On screen it is shown in the viewer's language: translated text first, with a caption "Auto-translated" and a tap to see the original. If the viewer's phone language equals the text's language nothing happens.
- Read-only places show the translation; fields the viewer edits keep their own text and show a translated preview line under them.
- Cache: localStorage `schwab.tr`, key `from|to|hash(text)`, bounded at 800 entries (oldest out), permanent otherwise; requests batched (<= 25) and only for text on screen. No hub, or offline, or `quota`: show the original with a one-line hint (once per session).
- The server translates in HTML mode so identifiers survive: drawing and task numbers (`E-301`, `T1019-02`), quantities with units and trade abbreviations (EMT, AWG, MC, GFCI) are wrapped `<span translate="no">`, newlines become `<br>`, and the result is unescaped. `selftest` proves a drawing number survives on the real service.
- Google Translate is machine translation: expect occasional wrong trade terms. The original is always one tap away.

## Security checklist (the review will check each)

- Keys never in URLs, logs, errors or the Sheet; PM key hash only; constant-time compare; a wrong key only ever gets 'unauthorized' (no global breaker, so one bad caller cannot lock out every phone); pushes are capped per role and per device.
- Role checks on every action server side; entity fields filtered by owner; crews cannot read other people's hours or any reports.
- Every inbound entity validated (types, caps, uid / date / time formats, strings clipped) before it is stored; Sheet writes RAW.
- Responses never include other roles' secrets; errors never echo submitted data; no stack traces.

## Opt-in multi-job protocol v2 (source prepared; not a live migration)

The existing deployment, original `SHEET_ID`, legacy role keys and v1 payloads remain valid. Every v1 request uses that original Sheet, regardless of any submitted `jobId`. The health response remains compatible. Do not rerun `setupHub`, replace the existing Sheet, rotate legacy keys, publish this source, or move phone data as part of merely reviewing this code.

V2 uses the canonical Electrical PM `projects.id` as `jobId`, never its display name. Each additional job receives its own empty Sheet and stable `instanceId`. Authentication looks up a hashed credential binding before reading the selected job's directory entry. Each job has separate revisions, cache/rate-limit keys, translation quota, archive state, weekly-repair state and operation receipts. A legacy job's v2 binding shares its original revision and Sheet with v1. Crew credentials still authorize the job's sent tasks; requested crew/person filters are display filters, not personal access control.

POST to the same existing `/exec` endpoint over HTTPS, with JSON in a `text/plain` body:

```json
{"v":2,"jobId":"canonical-project-id","key":"32-character-job-credential","action":"whoami"}
```

Every successful v2 response includes `jobId`, `instanceId` and `rev`. Validate both identities before consuming data. Role clients retain the existing role/action and field-merge rules, except `keys` and `rotate`: v2 credentials are individually bound and cannot be retrieved or rotated through a shared-role phone. Do not offer those old controls in v2. The separate server-only `bridge` principal allows only `whoami`, `pull`, `push`, and read-only `records`; it never returns a Sheet URL or another credential. `whoami` reports `role: "bridge"` and its capabilities. Its field writes use the PM merge partition; activity records identify the principal as `bridge`, not Harrison's platform identity. No owner-only PM content is accepted or stored by this Hub.

`pull` retains `{since,days}`: start at `since:0`; `days` is capped at 90 (14 by default). If `more:true`, repeat with `since:response.rev` until complete. This is an active window, not a historical export. `records` accepts `{kind,from,to,cursor?}` and returns `{items,cursor?}` (at most 200 items); carry its cursor until absent. A paged pull's `rev` is its delivered cursor. Request `whoami` for the current head when needed. Missing window records are not deletion markers.

Every v2 `push` additionally requires `opId` (8–80 ASCII letters, digits, underscore or hyphen) and integer `expectedRev`. A push of exactly one log and nothing else (no tasks, shifts, reports, config or deletions) may send `expectedRev: -1`, which skips the revision check: the entry is its author's alone and ordered by its own `at`, so no other writer can be overtaken; `-1` on any other push is `bad_request`. Keep the exact payload, bases, timestamps, revision and operation ID across network/busy/server retries. Requests are digested with sorted object keys, excluding the credential, and receipts are scoped to job, principal and proven device. Reusing an ID for different content returns `conflict`. A new operation with a stale expected revision also returns `conflict` before changing records; pull/rebase and use a new operation ID. The client does this in the same round, once (another phone writing since this one's last reply is the normal case on a busy job): it pulls, then pushes again under a new operation ID, so an online phone is never told its work is waiting for a connection. A second conflict in a row ends the round as before. A successful replay returns its original canonical result, whose revision may be lower than the present head.

Role clients may submit normal batches and config/deletions. The bridge submits exactly one task, shift, report or log per operation, with no config/deletion payload; a log goes with the `devSecret` of the phone it belongs to (device rules). Task base wrappers are `assignBase` and `crewBase`; shifts use `base`; reports use `supBase` and `pmBase`. Existing merge and refusal semantics still apply, including archived/deleted protection and PM/worker punch rules. An HTTP success with an entity `status:"rejected"` is a refusal, not a saved edit.

The `Operations` tab stores a prepared result and exact Sheets mutation plan before source writes. One atomic `spreadsheets.batchUpdate` applies entity rows, activity rows and the receipt's completion marker together. A durable per-job pending pointer causes the next request to recover that operation before another writer can move rows. Weekly totals are repaired after the atomic source commit and before acknowledgement. Receipts are retained indefinitely; they are not purged with field records. Never manually reorder/edit/delete this tab. The journal is scanned by operation key on each write, and the global script lock still serializes writes across jobs. The prepared journal has a 2,048,000-character limit; an oversized batch returns `too_large` without changing source rows. These are deliberate initial capacity ceilings.

The atomic write uses Google's documented [batch update transaction](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets/batchUpdate) and [typed cell update requests](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets/request). Text is written as `stringValue`, never interpreted as a formula.
